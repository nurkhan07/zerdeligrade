# ZerdeliGrade

Платформа проверки тестов и аналитики для сети образовательных центров **Zerdeli** (Казахстан).
Головной офис (ГО) управляет сетью; каждый центр видит только свои данные; учителя печатают
бланки ответов, фотографируют заполненные бланки, проверяют распознанные ответы и утверждают результаты.

Интерфейс на **казахском и русском** (переключатель на каждой странице, выбор сохраняется в профиле).

## Возможности

| Раздел | Что делает |
|---|---|
| Главная | Ученики, активные центры, тесты, обработанные бланки, средний %, очередь проверки, успеваемость по предметам и классам (или сравнение центров для ГО), сравнение периодов, последние проверки. Фильтры: период, предмет, класс; центр выбирается в шапке. |
| Тесты | Создание теста (предмет, параллель, язык, инструкция, проходной балл, время, штраф за неверный ответ). Редактор вопросов: один ответ (A–E, 2–5 вариантов) или «верно/неверно», баллы, текст вопроса и вариантов (необязательно), быстрый ввод ключа строкой `ABCDA…`. Публикация с проверкой полноты ключа; после публикации ключ заблокирован. Архив, копия, удаление черновика, назначение классам. |
| Шаблоны | Общие шаблоны Zerdeli (создаёт ГО) и шаблоны центра; «Использовать» создаёт черновик-копию в центре. |
| Бланки ответов | Партии бланков A4: на весь класс (по бланку на ученика), для одного ученика или пустые. Уникальный код и QR на каждом бланке, язык бланка kk/ru, предпросмотр и печать без интерфейса, скачивание PDF, отдельный ключ ответов для учителя. |
| Проверка по фото | Загрузка одного или многих фото (JPEG/PNG/WebP, с телефона или компьютера), определение теста и ученика по QR, распознавание, понятные ошибки, ручной ввод ответов, если фото не распознаётся. |
| Результаты | Фильтры (класс, предмет, тест, статус, даты), экран проверки: фото бланка, уровень заполнения каждого кружка, уверенность, предупреждения, исправление ответов, предварительный балл, утверждение, возврат на проверку с причиной, **аннулирование** ошибочного результата (с причиной; бланк можно проверить заново), история изменений, печатный отчёт, CSV, пакетное утверждение результатов без предупреждений. |
| Ученики | Добавление, изменение, отключение, поиск, фильтры, пагинация, импорт CSV с предпросмотром и проверкой (дубли кодов, неизвестные классы, возможные дубли имён), экспорт CSV, карточка ученика с динамикой. |
| Классы и группы | CRUD, закрепление учителей. |
| Аналитика | Средний % по предметам и классам, распределение, динамика по месяцам, сравнение с предыдущим периодом, самые трудные вопросы, частые неверные ответы, сводка по центрам (ГО). Считается в PostgreSQL только по утверждённым результатам. |
| Центры | ГО: создание, изменение, активация/деактивация. Администратор центра видит свой центр. |
| Пользователи и роли | Приглашение по почте, роли, право учителя утверждать результаты, отключение доступа. ГО назначает администраторов центров, администратор центра — учителей. |
| Общая база Zerdeli | Только ГО: сводка по всем центрам и поиск ученика по всей сети. |
| Журнал аудита | Все значимые действия; записи нельзя изменить или удалить (даже сервисным ключом). |
| Настройки | Профиль, язык, пароль, справочник предметов (ГО), удаление демо-данных (ГО), сведения о хранении фото. |

Роли: **Администратор Zerdeli (ГО)**, **Администратор центра**, **Учитель** (видит только закреплённые классы).

## Что реализовано и что нет

**Реализовано и покрыто автотестами**
- Схема БД (20 таблиц), RLS на каждой таблице, составные внешние ключи, не позволяющие ссылаться на записи другого центра.
- Подсчёт баллов только в PostgreSQL (`recompute_result`); браузер не может записать балл.
- Распознавание бланков (OMR) на TypeScript: поворот, перспектива, тени, слабое освещение, размытие, пустые, двойные и нечёткие отметки.
- Генерация бланков (SVG для печати и PDF), QR-идентификация, импорт CSV, аудит.

**Реализовано, но не проверено вживую в этой среде.** Здесь нет Docker и проекта Supabase, поэтому приложение собиралось (`npm run build`), но не запускалось против настоящего Supabase.
Перед вводом в работу пройдите [чек-лист приёмки](#чек-лист-приёмки) на тестовом проекте.

**Не реализовано (сознательно)**
- Проверка рукописных решений и развёрнутых ответов. Это отдельная функция: нужна модель OCR/vision и рубрика учителя. Простая загрузка фото такой проверки **не** выполняет.
- Кодирование ученика на бланке закрашиванием цифр (ID-сетка). Ученик определяется по QR персонального бланка или выбирается при проверке.
- Офлайн-режим и отдельное мобильное приложение. Веб-интерфейс адаптивен и работает в мобильном браузере с камерой.
- Внешние платные OMR/AI-сервисы не используются, ключи не нужны.

## Локальная установка

Нужны Node.js ≥ 20.9 (проверено на 24 LTS) и проект Supabase (облачный или локальный через `supabase start`, для него нужен Docker).

```bash
npm install
cp .env.example .env.local      # заполните значения, см. ниже
npx supabase link --project-ref <ref>
npx supabase db push            # применяет supabase/migrations
npm run dev                     # http://localhost:3000
```

Без настроенного Supabase приложение показывает страницу `/setup` с инструкцией, а не падает.

## Настройка Supabase

1. **Создайте проект** (регион ближе к Казахстану, например Frankfurt).
2. **Ключи** (Project Settings → API) запишите в `.env.local`:
   `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY` (**только сервер**, никогда с префиксом `NEXT_PUBLIC_`).
3. **Миграции:** `npx supabase db push`. Создаются таблицы, RLS, функции, закрытый бакет `answer-sheets` и справочник предметов.
4. **Auth → URL Configuration:** Site URL = адрес приложения; в Redirect URLs добавьте `https://<домен>/auth/confirm`.
5. **Auth → Providers → Email:** отключите самостоятельную регистрацию (сотрудников только приглашают).
6. **Auth → Email Templates:** для «Invite user» и «Reset password» вставьте содержимое `supabase/templates/invite.html` и `recovery.html`. Ссылки ведут на `/auth/confirm`.
   Для рабочих рассылок подключите свой SMTP: встроенная почта Supabase сильно ограничена по количеству писем.
7. **Первый администратор ГО.** Создайте пользователя (Auth → Users → Add user или Invite), затем в SQL Editor:
   ```sql
   update public.profiles set is_hq_admin = true where email = 'admin@zerdeli.kz';
   ```
   Роль ГО нельзя получить через интерфейс или API: колонка `is_hq_admin` закрыта для записи с клиента.
8. Войдите, создайте центры (Центры), пригласите администраторов центров (Пользователи).

## Деплой на Vercel

1. Импортируйте репозиторий (Framework: Next.js; корень — папка `zerdeligrade`).
2. Environment Variables: все переменные из `.env.example`. `NEXT_PUBLIC_SITE_URL` = боевой адрес, `CRON_SECRET` = длинная случайная строка.
3. `vercel.json` запускает ежедневный cron `/api/cron/retention` (удаление фото по сроку хранения). Vercel передаёт `Authorization: Bearer $CRON_SECRET`.
4. После деплоя обновите Site URL и Redirect URLs в Supabase.
5. Фото уменьшаются в браузере до 2400 px перед загрузкой, поэтому лимит тела запроса Vercel (4,5 МБ) не мешает.

## Безопасность и проверка RLS

- **Запрет по умолчанию:** RLS включён на всех таблицах; у `anon` нет прав ни на одну таблицу или функцию.
- Клиент **не может записывать** в `center_memberships`, `scan_jobs`, `recognized_answers`, `assessment_results`, `result_answers`, `result_reviews`, `audit_logs`, `file_metadata`. Изменения идут только через функции `SECURITY DEFINER`, которые повторно проверяют права, или через сервер после проверки сессии пользователя.
- Баллы считает только `public.recompute_result`. Проверка, утверждение и возврат идут через `review_result`, `finalize_result` и `reopen_result`, каждое изменение пишется в `result_reviews` и `audit_logs`.
- Нерешённые предупреждения распознавания (двойная отметка, нечёткая отметка, нет ученика, сильное размытие) **блокируют** утверждение на уровне БД.
- `center_id` нельзя изменить (триггер); дочерние записи ссылаются на родителя составным ключом `(id, center_id)`.
- Пользователь может изменить в профиле только имя и язык (права на уровне колонок).
- Сервисный ключ используется только на сервере (`import "server-only"`), фото доступны по подписанным ссылкам на 5 минут после проверки RLS.
- Заголовки безопасности (`X-Frame-Options`, `nosniff`, `HSTS`, `Referrer-Policy`), proxy обновляет сессию, каждая страница и каждое действие перепроверяют пользователя.

**Ручная проверка межцентрового доступа** (SQL Editor, подставьте UUID двух пользователей разных центров):
```sql
begin;
set local role authenticated;
select set_config('request.jwt.claim.sub', '<uuid администратора центра A>', true);
select count(*) from public.students where center_id = '<uuid центра B>';     -- должно быть 0
insert into public.students (center_id, first_name, last_name)
  values ('<uuid центра B>', 'x', 'y');                                       -- ошибка: row-level security
update public.profiles set is_hq_admin = true where id = auth.uid();         -- ошибка: permission denied
rollback;
```

### Чек-лист приёмки
1. ГО создаёт два центра, приглашает администратора в каждый (письма приходят, пароль устанавливается).
2. Администратор центра A не видит центр B ни в одном разделе, включая экспорт CSV.
3. Учитель видит только закреплённые классы и их учеников.
4. Тест на 20 вопросов → публикация → бланки на класс → печать в масштабе 100% → заполнить ручкой → сфотографировать телефоном → проверка по фото.
5. Двойная отметка блокирует утверждение до исправления; изменения видны в истории и в журнале аудита.
6. Аналитика меняется после утверждения результатов.

## Бланки и распознавание (OMR)

- Разметка задана в одном месте (`src/lib/omr/layout.ts`, `LAYOUT_VERSION`). Её используют печать (SVG), PDF и сканер, поэтому они всегда совпадают.
- Бланк A4: 4 сплошные угловые метки 8 мм, ориентационная полоса у левой верхней метки, QR `ZG1:<код>`, до 120 вопросов (4 колонки × 30), кружки A–E Ø 4,6 мм.
- Алгоритм: адаптивная бинаризация → поиск меток → проверка геометрии (размер меток согласован с масштабом, белое поле вокруг) → гомография (исправляет поворот, наклон и перспективу) → выбор ориентации по полосе → уровень заполнения каждого кружка относительно локальной белизны бумаги → классификация: `ok` / `blank` / `multiple` / `uncertain` с уверенностью → проверка совмещения сетки → чтение QR с выпрямленного фрагмента.
- Пороги: заполнен ≥ 0,50; пуст ≤ 0,28; между ними «нечётко». Нечёткие и двойные отметки **никогда не засчитываются молча**: результат получает статус «Требует проверки».
- Перед реальным использованием проверьте пороги на 30–50 настоящих бланках, заполненных вашими ручками и карандашами, при вашем освещении (`THRESHOLDS` в `recognize.ts`).
- Печать: только 100% (без «Подогнать по размеру»), белая бумага, лазерный принтер предпочтительнее.

## Персональные данные, согласие, хранение

Платформа обрабатывает данные несовершеннолетних, поэтому собирается минимум:
- Об ученике хранятся только имя, фамилия, класс, внутренний код и статус. Нет даты рождения, ИИН, адреса и телефона.
- Фото бланков лежат в закрытом бакете, публичных ссылок нет; доступ по ссылке на 5 минут, каждый просмотр пишется в аудит. При сохранении фото перекодируется, метаданные EXIF и GPS удаляются.
- Срок хранения фото — `FILE_RETENTION_DAYS` (по умолчанию 365 дней). Затем фото удаляются автоматически, результаты остаются.
- Сохраняется уменьшенная копия фото (до 1600 px, около 80–250 КБ). Распознавание выполняется по полному снимку до уменьшения.
- **Организационные меры (ответственность центров):** получить согласие родителей или законных представителей на обработку данных и результатов тестирования согласно Закону РК «О персональных данных и их защите»; назначить ответственного; определить сроки хранения; обрабатывать запросы на доступ и удаление (ученика можно отключить, а при необходимости администратор БД удаляет запись и её результаты каскадно).

## Демо-данные

```bash
npm run db:seed-demo     # 2 демо-центра «Zerdeli Demo», классы, 48 учеников, тесты и результаты
npm run db:remove-demo   # удалить всё демо (или Настройки → «Удалить все демо-данные»)
```
Все демо-записи помечены `is_demo` и значком «Демо» в интерфейсе. Логины демо-пользователей и их случайные пароли скрипт печатает только в вашем терминале.

## Как изменить срок хранения фото

Срок задаётся числом дней в переменной `FILE_RETENTION_DAYS`. Например, `90` — фото хранятся 3 месяца, потом удаляются; результаты и оценки остаются навсегда.

**На своём компьютере**
1. Откройте `zerdeligrade\.env.local` в Блокноте.
2. Найдите строку `FILE_RETENTION_DAYS=365` и замените число, например на `FILE_RETENTION_DAYS=90`. Если строки нет, добавьте её.
3. Сохраните файл и перезапустите сайт: остановите `npm run dev` (Ctrl+C) и запустите снова.

**На Vercel**
1. Project → **Settings → Environment Variables** → `FILE_RETENTION_DAYS` → **Edit** → новое число → **Save**.
2. **Deployments** → у последнего деплоя меню **⋯ → Redeploy**. Без нового деплоя значение не применится.

**Важно знать**
- Новый срок действует для **новых** фото: дата удаления записывается в момент загрузки.
- Чтобы применить новый срок и к **уже загруженным** фото, выполните в Supabase → SQL Editor (замените `90` на ваше число):
  ```sql
  update public.file_metadata
     set delete_after = created_at + interval '90 days'
   where deleted_at is null;
  ```
- Удаление выполняет ежедневная задача `/api/cron/retention`. Её запускает Vercel (настроено в `vercel.json`, нужна переменная `CRON_SECRET`).
  Пока сайт работает только на вашем компьютере, задача сама не запускается: просроченные фото удалятся после выкладки на Vercel.
- Допустимые значения: от 1 до 3650 дней. Неверное значение заменяется на 365.
- Новое значение также отображается в «Настройки → Данные и конфиденциальность».

## Аннулирование результатов

Если учитель сфотографировал не тот бланк, фото испорчено или результат ошибочен, результат можно **аннулировать** на его странице (кнопка «Аннулировать», причина обязательна):
- **Неутверждённый** результат аннулирует учитель, который его видит, или администратор центра.
- **Утверждённый** результат аннулирует только администратор центра (или ГО).
- Результат не удаляется бесследно: он пропадает из списков, аналитики и экспорта, но остаётся в истории и в журнале аудита (кто, когда, почему). Посмотреть аннулированные можно в «Результатах» через фильтр статуса «Аннулировано».
- Бумажный бланк освобождается, его можно сфотографировать и проверить заново.
- Фото аннулированного результата сразу удаляется из хранилища.

## Обновление базы данных

Если база создавалась файлом `supabase/setup-all.sql` **до** появления аннулирования, выполните один раз в Supabase → SQL Editor содержимое файла
`supabase/updates/001_void_results.sql` (Ctrl+A, Ctrl+C → New query → Ctrl+V → Run). Без этого страница результата не откроется.
Новые установки делают это автоматически: файл `setup-all.sql` уже включает обновление.

## Регистрация сотрудников с кодом из почты

Сотрудник может зарегистрироваться сам: **страница входа → «Нет аккаунта? Зарегистрироваться»**.
1. Он вводит ФИО, почту и пароль, получает на почту **код из 6 цифр** и вводит его на сайте.
2. Выбирает свой центр и отправляет заявку. Пока заявку не одобрят, никакие данные ему не видны.
3. Администратор центра (или ГО) видит заявку вверху раздела **«Пользователи и роли»**. «Одобрить» даёт роль «Учитель» без права утверждать результаты (это можно изменить там же), «Отклонить» требует причину, которую увидит заявитель.
4. Дальше сотрудник входит **по почте и паролю**. Письмо с кодом отправляется только при регистрации.

В списке для заявки показываются только активные **не демо** центры. Сначала создайте настоящий центр в разделе «Центры».

**Настройка в Supabase (один раз):**
1. Выполнить `supabase/updates/002_access_requests.sql` в SQL Editor.
2. Authentication → Sign In / Providers → Email: **Allow new users to sign up = ON**, **Confirm email = ON**.
3. Authentication → Emails → **Confirm signup**: вставить содержимое `supabase/templates/confirmation.html` (в письме должен быть `{{ .Token }}`).
4. Подключить свою почту: Authentication → Emails → **SMTP Settings** (Resend, Brevo или почта Zerdeli). Без этого письма уходят только адресам вашей команды Supabase.
